## 1. 产品目标与学习闭环

204 面向个人考研英语学习，以句子为最小复习单元。用户从真题中选出需要反复理解的句子，通过看英文、听整句、听重点词、查看中文和双语分块，逐步读懂文章。重点词保留在句子语境中。

```mermaid
flowchart LR
    P[真题文章与手工标注] -->|选中句子同步| S[句库与重点词]
    I[单句新增与批量导入] --> S
    S --> A[整句译文、词卡、双语分块、音频]
    S --> Q[固定周期的复习安排]
    A --> R[看句子、听音、查看翻译]
    Q --> R
    R --> E[播放事件与安排完成记录]
    E -->|下一周期重新计算| Q
```

“句子持续循环复习”与“本轮安排完成”是两个层次：句子没有永久毕业状态，同一句可以在当前周期出现两次，每次安排有独立完成记录，之后仍进入后续周期。

例如，句库中的句子 A 只保存一份内容，本轮清单可以安排“A 第一次”和“A 第二次”。完成第一项不会自动完成第二项；两项均完成后，表示 A 在本轮的任务完成，下轮仍会参与安排。这里是在解释内容与完成记录各自的职责，这种行为本身没有问题。

## 2. 当前界面与操作

| 入口 | 当前职责 | 主要实现 |

| `/library` 句库 | 搜索与排序、句子编辑和删除、播放次数、音频状态、逐句音色、跨句关联词 | `EnglishLibraryView.vue`、`useEnglishSentenceList.js` |
| `/passages` 阅读 | 今日文章、年份及题型筛选、正文编辑和加粗标注、自动保存、选句同步、完成阅读 | `EnglishPassagesView.vue`、`usePassageEditor.js` |

顶部导航有复习、句库、阅读、统计四项；新增是独立路径。旧 `/english/...` 路径保留跳转兼容。

复习页默认每页 20 项，句库默认每页 40 句。中文默认隐藏，重点词释义可直接查看。快捷键包含 Space 播放、Enter/J 完成并下一句、W/S 或方向键移动、T 显示翻译，以及数字键或 Q/E/R/F/G 播放重点词；文本输入和中文输入法有独立处理。

阅读页的“今日文章”每次最多选两篇，默认优先阅读理解，尽量覆盖英语一和英语二；当天已完成文章继续保留在今日列表。它根据文章状态、题型、年份和 Text 编号计算，与句子复习轮次分别运行。

文章标注用 `**...**` 保存；富文本编辑器与 Markdown 文本相互转换。已有文章在输入停止 900ms 后触发自动保存，新文章先通过手动保存建立记录。切换文章、切换主导航和退出登录会经过文章保存处理。选句目前按标点正则切分，只提取包含手工重点标记的句子。

累计播放计数包含旧系统导入历史，现有事件表只覆盖部分历史。例如，只按当前事件逐条相加，会漏掉导入时保留的累计次数；重构统计时仍需保留这部分历史。

当前存储分工如下，这是一种正常的存储方式：

| 内容 | 存在哪里 | 用途 |
| --- | --- | --- |
| 句子、文章、当前译文、词义、累计次数和本轮完成进度 | SQLite 数据库 | 日常学习使用的内容与记录 |

代码结构调整可以继续使用现有数据库和文件。若以后涉及搬服务器或数据迁移，再保留数据库及需要沿用的音频；是否一并迁移历史审校报告，取决于是否需要保留其追溯能力。仅复制 Git 源码不等于复制了当前学习内容和文件。

## 4. 三类行为记录与周期规则

| 用户行为 | 持久化结果 | 对复习安排的作用 |
| --- | --- | --- |
| 开始一次整句播放 | `review_count + 1`，写入 `sentence_play` | 增加曝光，不自动完成安排 |
| 播放重点词 | 对应词播放次数及 `word_play_total` 增加，写入 `word_play` | 参与当前句与跨句计算，不自动完成安排 |
| 完成并下一句 | 标记指定 `round_item_id`，成功首次完成才增加 `completion_count` 并写入 `sentence_review` | 完成该次安排 |

前端以 `round_item_id` 标识复习卡片实例，普通句库使用 `sentence_id`。同一句的两个复习实例需要分开保留进度。`createReviewEventQueue.js` 对同一卡片实例的播放及完成写入进行串行处理。

复习约定与实现入口见 [review_rounds.py](../backend/app/english/review_rounds.py)、[repository.py](../backend/app/english/repository.py) 和 [main.py](../backend/app/main.py)：

- 周期长度为 7 天，以北京时间 08:00、即 UTC 00:00 为边界。
- 启动时补偿到期周期，运行时后台线程每 15 秒检查；列表请求提供补偿路径。
- 周期中的安排保存句子成员、排列和重复项；中途新增句子进入下一周期。首次建轮会纳入当时全部活动句子。
- 冻结的是安排，句子内容仍从句库读取最新值；软删除的句子会从展示队列中过滤。
- 提前全部完成后等待完成时刻之后的下一个边界，再创建新周期。
- 前端按到期时间或提前完成后的下一边界刷新，重新进入复习时可定位首个未完成分页。
- 七天是周期长度；当前安排没有逐日解锁机制，整轮允许提前完成。

## 5. 排序与重复次数是两套计算

以下是 [ranking.py](../backend/app/english/ranking.py) 的现有实现，不代表新的算法提案。用户已确认两套计算是有意设计：一套回答“先复习哪句”，另一套回答“本轮出现几次”，重构基线是保留各自的计算规则。

### 5.1 哪句排在前面

排序首先使用每句自己的整句播放次数和重点词播放信号。设某词播放次数为 `c`：

```text
g(c) = 0                                      当 c = 0
g(c) = (1 - 0.35^c) / (1 - 0.35)             当 c > 0
E_sort = 整句播放次数 + 0.2 × Σ g(每个重点词播放次数)
peak = max(3, 当前参与计算句子的平均 E_sort)
familiarity = sigmoid((E_sort - peak) / 2)
base_score = 1 - familiarity + 未播放整句时的 0.08 加成
```

再用跨句词网络调整分数：薄弱词加成最多 0.16，语境多样性加成最多 0.06，已熟悉词惩罚最多 0.08。词形归并使用小写、简单词尾规则以及当前语料中已有词形的频次，没有独立的词汇知识库。

按分数排序后，还会在前 80 个候选中，依据最近 6 句的重点词重合情况施加 0.12 的重合惩罚，减少相邻句子反复出现同一重点词。

生成最终安排时，将整句播放、重点词播放、完成次数均为零的句子移到优先位置，同时保留组内排序。

### 5.2 本轮安排一次还是两次

重复次数另行计算，使用跨句汇总的重点词播放次数，以及这些词在参与计算的句子中出现的次数和频次排名：

```text
E_repeat = 本句整句播放次数
           + Σ(词在语料中的累计播放次数 × 词频百分位权重 × 词在本句出现次数)
p = 本句 E_repeat 在参与计算句子中的百分位；并列取平均排名
repeat_count = 1 + floor(sin(2πp)^2 + 0.5)，限制在 1 或 2
```

因此重复分配在约 25% 和 75% 百分位附近较高。需要重复的句子在基础遍历后再出现一次。排序响应里的 `algorithm.exposure` 与安排里的 `review_exposure` 分别服务于上述两种决策，重构时分别保留两套计算的业务含义和行为。

当前算法没有按每个句子的遗忘时长计算独立的下次到期日期；时间主要控制整轮切换。

## 6. 翻译和审校系统

在线自动加工由 [translation_generation.py](../backend/app/english/translation_generation.py) 调用 [translator.py](../backend/app/english/translator.py)。主要流程是：

1. 清理重点词 Markdown 标记和含中文的方括号编辑注记，取得英文来源文本。
2. 提取语义要点并生成整句初稿，再独立终审。特定复杂结构会从英文结构独立重译。
3. 基于定稿生成重点词卡，区分“本义”和“句中”，附可选短提示；中英文证据要能在输入中逐字定位。
4. 通过双语原文短语定位切点，由程序截取分块，保持原文覆盖和对齐。
5. 本地校验，针对问题词卡或分块局部重试；无法可靠切分时允许整句一块。

相邻上下文当前主要通过句库 ID 前后三句取得，供词义、指代和专名消歧；它没有通过文章关联恢复完整原段落。若后续调整 AI 上下文，需同时支持来自文章和独立导入的句子。

整句缺译时运行完整流程；整句已有译文而新重点词缺释义时，只补词卡。写回会检查英文是否仍与请求开始时相同，并保留当前已填值。修改英文会触发旧翻译和音频的失效判断；只改变重点标记与修改正文的处理不同。

AI 配置集中于忽略的 `.env.secrets.local`，启动时在 `.env.local` 之后加载，使用 `STUDY_ENGLISH_AI_*`。底层请求为兼容的 `/chat/completions` HTTP 接口，具有进程内共享节流和有限瞬态重试。[2026-09-08 实测记录](translation-full-retranslation-20260908.md)记载的批次使用 `deepseek-v4-flash-0731`；模型是运行配置，不能把历史批次值视为不可变业务规则。

线下审校是单独的一条工作流：

```text
evaluate_translation_pipeline
  → inspect_translation_evaluation + 审阅决策文件
  → repair_translation_evaluation（整句 / 词卡 / 分块）
  → 必要时 reconcile_translation_focus（保留并发新增重点词）
  → finalize_translation_evaluation
  → apply_translation_evaluation（预检、备份、事务内复检和写入）
```

还有 AI 判断与复判脚本、无 AI 的规则回归脚本，以及较早的批量重译和数据修复入口。它们是项目维护能力的一部分，迁移时需要盘点其直接写库路径。

学习数据库保存当前翻译、分块、词义和提示。详细候选、词卡引文、模型及代码指纹、修订历史、审阅决策主要在 `backend/data/audits/` 的报告中；本次确认全量重译审计目录仍存在。数据库支持日常展示，报告用于追溯“译文如何经过审阅和修改成为当前版本”；仅有当前翻译字段无法重建这一过程。

历史全量审阅结果与未来在线自动生成的结果具有不同验证范围。重构时需要保留“调用成功”“本地校验通过”“经过源文审阅”之间的区别。

## 7. 音频系统

整句支持 Edge TTS 和本地 Kokoro；词音频使用 Edge TTS。现有目录提供 28 个 Kokoro 和 4 个 Edge 整句音色，支持全局默认、逐句覆盖及试听。

整句音频版本根据正文、供应商和音色计算哈希。元数据与文件共同决定整句音频是否可播放；旧文件存在不等于它仍对应当前正文。整句音频生成结果写回时会检查版本，避免旧任务覆盖新文本的音频。

Kokoro 在子进程中加载模型、生成 WAV，并做响度处理；批次结束回收子进程。整句后台生成有进程内串行锁。本地模型、词形及音素处理依赖和 ffmpeg 都属于实际运行条件。

前端由 `useEnglishAudio.js` 管理整句与词音频互斥、Blob 缓存、页面切换时释放资源，以及最多 3 个并发请求的预加载队列。试听音频由音色设置模块单独管理。

自动翻译和自动音频任务主要依靠 FastAPI `BackgroundTasks`、启动恢复线程以及句子字段中的待处理状态；没有独立的持久化任务表。前端主要通过后续查询刷新状态。重构异步任务时，需要明确任务版本、失败反馈、恢复方式及资源释放职责。

## 8. 实际代码架构与部署

当前依赖以 [frontend/package.json](../frontend/package.json) 和后端 requirements 为准：Vue 3、Vue Router、Vite、Tailwind CSS、Lucide；HTTP 使用原生 `fetch`。后端是 FastAPI、Pydantic、SQLite 原生连接和 SQL。旧设计文档中的 Pinia、Element Plus、Axios 描述不符合当前依赖。

```text
App.vue：登录状态与登录页
└─ StudyApp.vue：导航、URL 与切换前的文章保存
   └─ EnglishFlow.vue：按 mode 组合界面和状态
      ├─ useEnglishSentenceList：句库、复习列表、编辑、统计刷新
      ├─ useReviewNavigator / createReviewEventQueue：导航与复习写入
      ├─ useEnglishAudio / useEnglishAudioSettings：播放和音色
      └─ EnglishPassagesView → usePassageEditor：文章工作区

main.py：组装 API、初始化与启动恢复
├─ platform：SQLite、账号会话、写入来源检查、AI HTTP 传输
└─ english/api.py：业务接口和后台任务触发
   ├─ repository.py：句子 SQL、业务操作、序列化、音频元数据、安排协调
   ├─ passages.py / stats.py：文章与统计
   ├─ ranking.py / review_rounds.py：排序、重复和周期状态
   ├─ translation_generation.py → translator / quality / glossary / transport
   └─ audio_generation.py → Edge TTS / kokoro_worker.py
```

路由没有为每个功能页创建完全独立的顶层业务实例；`StudyApp` 保留一个 `EnglishFlow`，通过 `mode` 切换。前端虽然已经拆分视图，列表、分页、统计和异步响应仍有共享状态。

`repository.py` 约 1896 行，除数据库访问外还负责编排多类行为；翻译模块同时包含提示词、结构修复、兼容旧返回格式、校验反馈及重试。源文件规模约为后端运行代码 9284 行、后端脚本 7933 行、前端源码 6708 行，包含相应测试和支持代码。重构范围应按业务职责识别，不能用文件数量直接代替模块边界。

默认运行链路为：

```text

  → 本地前端服务 127.0.0.1:5204
      ├─ frontend/dist 静态资源与 SPA 路由回退
      └─ /api 转发 → 127.0.0.1:8204 → SQLite / 媒体文件 / AI / TTS
```

`start-dev.sh` 当前也先构建再运行 Python 静态代理；`npm run dev` 才是 Vite 开发服务器。`deploy.sh` 创建并重启两个 systemd 服务。`platform/` 是本仓库内部基础设施，系统不依赖 302、408 或外部共享平台代码。

账号采用单用户 Cookie 会话，存储在 SQLite，默认期限 14 天；写操作有来源和专用请求头校验。数据库使用 WAL、外键及写入等待，部分读改写操作使用 `BEGIN IMMEDIATE`；升级主要依靠启动时加列、迁移和修正，没有独立的版本化迁移框架。

`study.db` 被 Git 跟踪但本机标有 `skip-worktree`；新增媒体、模型和审计文件被忽略。数据库用 SQLite online backup，媒体需要单独备份。若以后涉及换机器或数据迁移，需要按实际保留范围备份数据库、媒体和审校记录；代码结构重构可以继续沿用现有存储。

## 9. 重构讨论中的职责边界

| 边界 | 当前实现 | 后续设计中的关注点 |
| --- | --- | --- |
| 内容与来源 | 文章保存句子 ID 数组，文章提取句子和历史独立句子并存 | 保留独立句子的完整使用能力；新增来源定位按具体功能需要设计 |
| 重点词与标注 | 加粗文本、词卡字典、播放字典及计算时词形归并共同表达一个概念 | 是保持句内词卡，还是引入词项、词形及语境实例 |
| 学习事件与复习安排 | 累计次数、事件明细、轮次条目和 UI 状态共同影响反馈 | 哪些是学习事实，哪些是可重算安排，哪些只是界面状态 |
| 排序与重复策略 | 用户有意采用两套曝光计算，分别决定顺序和本轮次数 | 分别保留计算规则，验证重构前后的排序、重复次数和周期行为 |
| 内容版本与生成产物 | 翻译依赖原文和中文定稿，音频依赖原文与音色 | 什么变化使哪种产物失效；旧任务如何停止或拒绝写回 |
| 在线生成与线下审校 | 运行接口与多个脚本分别调用生成、校验和写库 | 哪些共用应用服务，哪些保留独立审计及应用阶段 |
| 页面状态与异步回写 | `EnglishFlow` 及列表模块共享较多状态，文章有多条保存路径 | 请求返回后写入哪个页面、哪个版本；何时清理计时器和音频 |

可讨论的职责划分是：语料与来源、文章标注、句子及句内词卡、复习安排、学习事件统计、翻译加工审校、音频资产；登录和本地存储继续作为基础设施。这只是分析现有职责的方式，尚未选择新的目录结构、框架或数据库。

## 10. 已有验证和已知问题

本轮理解工作沿用前一轮同一代码基线的验证结果：前端 24 项测试、后端 9 项平台和 34 项英语可靠性检查、编译、模块边界、构建及健康检查通过。后端可靠性检查在数据库副本上执行。健康检查只证明服务可响应，现有测试也没有覆盖所有交互和恢复场景。

前一轮独立复现的问题应成为重构验收案例：

1. 统计刷新用活动句子数覆盖复习安排总数，导致含重复项的队列分页缩短。
2. 跨多个周期补偿后，边界规范化把新周期回退，后续检查重建刚完成过条目的安排。
3. 文章同步响应直接替换正文并清除脏标记，覆盖请求等待期间的新编辑。
4. 审阅记录只绑定报告名和句子 ID，同名报告追加的新候选能够沿用旧的接受记录。

本次只读梳理没有重新调用外部 AI 或执行批量生成，也没有新增对译文语义准确率的判断。后续重构目标、需要改变的学习流程、历史数据迁移策略和上线方式仍应由具体讨论确定。
